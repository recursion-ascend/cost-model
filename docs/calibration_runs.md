# 要哪些上板 run 才能把系数定下来

本模型的**结构**已经相当完整 (编排维度见 `design_space_gaps.md` 的速查表), 现在的瓶颈是
**系数**。下面每一项都写清: 固定什么 / 扫什么 / 从 trace 取哪个量 / 能定哪个常数 / 怎么验。

通用要求 (不满足就白跑):

* **一次只动一个变量。** 本仓在搬运口径上栽过两次 —— 先据 bs36 与 bs8192 把载入改成
  `max(A,B)`, 又被 bs128 推翻, 原因就是那两个 run 里 **m 与"每专家 m-group 数"一起变**。
  清单里每一项都显式写出"必须固定"的那些量。
* **trace 要每个事件带 `dur`** (现有 20260930 的 run 就是这个格式: `GMM1·wN` / `GMM2·wN` /
  `ACT_QUANT·wN` / `COMBINE` / `DISPATCH_XFER` / `DISPATCH_LOCAL`, 以及 `WAIT_*`)。
  取**中位数**而不是均值, 并同时记 p10/p90 —— 首波常含流水填充, 要能看出来。
* **记下并发核数。** 同一个量在不同并发下不是一个数 (见 R2), 所以每个 run 都要能数出
  "同时在跑这个 stage 的核数" (trace 的 `tid` 去重)。
* 每个 run 都附 `tiling_rank0.bin` 或等价的 tiling 真值, 否则护栏对不了几何。

---

## R1 — Cube 效率系数 (最该先做, 一个 run 就够)

| | |
| --- | --- |
| 为什么缺 | 规格峰值已填 (`cube_mac_per_us("fp8")` = 1.35e7 MAC/µs), 但**达成率**未知。现有 run 反解只有峰值的 24%, 而那批形状是**载入绑定**的 —— 用它当效率系数等于把"当时恰好载入绑定"烧进常数。 |
| 固定 | `tile_m` / `tile_n` / `K` / 并发核数 / 数据类型 |
| 扫 | 不用扫。要一个**计算绑定**的形状: 把 m 做大 (m ≥ 512) 让 A 流时间超过 B 流, 或把 `tile_n` 调大让计算量相对载入变大。 |
| 取 | `GMM1·w0` 与 `GMM2·w0` 的单 tile 中位时长 |
| 定 | `efficiency` = 模型按峰值算出的计算时长 / 实测时长 (在计算绑定区才有意义) |
| 验 | 同一 run 里换一个 `tile_n`: 效率系数应当基本不变 (它是单元效率, 不是形状效应) |

判断是否落在计算绑定区: 模型给的 `compute_us > load_us` (`gmm1_phases` 返回这两项)。

## R2 — `BW_L1_GM` 按并发分档 (结构可能要改, 优先级高)

| | |
| --- | --- |
| 为什么缺 | 它是**单核**带宽, 但实测随并发核数变: 由 A 流斜率反解, 28 核 45.3 GB/s、18 核 37.0 GB/s。一个常数满足不了两档。另外 950PR 在 28 核上已抵消聚合 HBM 的 91%, 核再多就突破物理上界。 |
| 固定 | `tile_m` / `tile_n` / `K` / 每专家 m-group 数 / m |
| 扫 | **并发核数**: 4 / 8 / 14 / 20 / 28 (用 `aic_num` 或只让部分核有活) |
| 取 | `GMM1·wN` 单 tile 中位时长; 同时数该波的 `tid` 去重数 = 真实并发 |
| 定 | 每档的单核有效带宽; 看它是"常数"、"聚合 ÷ 并发"还是两者取小 |
| 验 | 把每档的 单核带宽 x 并发 画出来: 若曲线在高并发处压平, 平台值就是聚合上限, 应与规格 (950PR 1.6 TB/s / 950DT 4 TB/s) 对得上 |

**这一项可能改模型结构**: 如果曲线显示聚合上限在实用并发区就起作用, 那 `BW_L1_GM` 不该是
常数, 而应是 `min(单核上限, 聚合/活跃核数)` —— 这个形式已经在
`PlatformSpec.gm_bw_per_core` 里备好了, 只是缺省没启用。

### R2b — A 流斜率 (顺带就能拿到, 不用单独跑)

同一组 run 里固定并发与几何、**只扫 m** (例如 64 / 128 / 192 / 256), 单 tile 时长对 m 的
斜率 = `K / BW_A`。这是目前最干净的带宽标定手柄 (几何与并发都固定, 只有一个变量)。
它也顺便复核搬运口径: 斜率为 0 就说明 `max(A,B)` 对, 非 0 则相加对 (现有两点给的是非 0,
见 `tests/test_load_convention.py`)。

## R3 — COMBINE 的落点跨度系数 (缺口 10 的另一半)

| | |
| --- | --- |
| 为什么缺 | 实测对 m **超线性** (m 比 3.56 倍 -> 时长比 6.62 倍), 而按字节与按每行固定开销都是线性的。结构已备好 (`combine_layout` -> `spread_slots` -> `scatter_us_per_row` / `scatter_exponent`), 系数缺省 0。 |
| 固定 | **m 与 n 必须固定** (这是关键: 现有三个 run 里 m 与 token 数一起变, 分不开) |
| 扫 | **token 数**: 例如固定每专家 256 行, 让 token 数取 256 / 512 / 1024 / 2048 (靠调 topk 或专家数保持 m 不变) |
| 取 | `COMBINE` 单事件中位时长; 另记该 run 的 token 数 x topk = 跨度槽位数 |
| 定 | `scatter_us_per_row` 与 `scatter_exponent`: 对 `(时长 - 字节项) / m` 与 `跨度/m` 做回归 |
| 验 | 三个点以上才下指数结论; 再用一个 `expert_contiguous` 的 run (若 kernel 支持) 检查跨度 = 行数时该项应趋近 0 |

**顺带必须记一笔**: 读侧 (UNPERMUTE 从顺序读变 gather) 现在**完全没建模**, 所以填了写侧
系数之后 `expert_contiguous` 会显得单方面变好。要让这笔交换两侧都算得出, UNPERMUTE 也得
有它自己的跨度项 —— 那需要一个"真的改了布局"的 kernel 变体来标。

---

## R4 — `BW_REMOTE_WRITE` (现在是 assumed)

| | |
| --- | --- |
| 为什么缺 | 取的是远端读的对称值 31 GB/s, 从没标过。聚合上没矛盾 (31 x 28 = 0.87 TB/s, 占灵衢 2.0 的 43%), 但实测 bs36 单 tile 5.676 µs 而模型给 1.189 —— 差 4.8 倍。这个差与 R3 的跨度项纠缠在一起, 所以 **R3 与 R4 要一起看**。 |
| 固定 | token 数 (即固定跨度) / m / 并发核数 |
| 扫 | **每行写出的字节数**: 调 `tile_n` 或 `h`, 让单次 `DataCopyPad` 的 blockLen 取 256B / 512B / 1KB / 2KB / 4KB |
| 取 | `COMBINE` 单事件中位时长, 拆出跨卡行的那部分 (或做一个全跨卡 run: 所有 token 来自其他卡) |
| 定 | 跨卡写的"固定开销 + 带宽"两项 —— 小包时固定开销占主导, 这正是现在缺的 |
| 验 | 大包处的斜率应当收敛到一个带宽值, 且不超过规格互连带宽 |

## R5 — `BW_UB` 重标 (优先级低)

出处是"按 `ACT_BYTES_PER_VEC=580` 在单点上反解", 而那个 580 后来改成了 722 (源码计数,
旧值漏了 `ComputeFp8Data` 那一遍), 所以 93 GB/s 这个数的推导前提已经不成立。

固定几何, 扫 ACT 的 m (或 `logical_n`), 取 `ACT_QUANT·wN` 单 tile 中位时长对字节量的斜率。

## R6 — URMA PUT (只在要评估 Layered 路径时才需要)

`URMA_PUT_LAT_US` / `URMA_PUT_BW_SINGLE` 都是"取 GET 的对称值", 没标过。要一个
`topo_urma=true` 的 run, 固定批大小扫 PUT 字节量。

## R7 — 晚绑定的取活开销 (新增 2026-10-05; 它现在是唯一让一条结论完全无法判定的缺口)

`PrimitiveCosts.late_bind_fetch_us` 缺省 **0.0**, 出处 assumed —— **0 不表示"没有代价",
表示本模型没有声称代价是多少**。

### 为什么它比 R1~R6 更要紧

静态分核 ("我干哪些 tile" 编译期算好) 运行时零开销; 晚绑定是运行时从一个共享游标抢活,
真实 kernel 得做一次原子加 (或一次核间同步标志的读改写)。不计这笔, **晚绑定就只拿收益
不付代价, 永远显得更好** —— 那是模型的结构偏置, 不是结论。

实测这个偏置有多大 (examples/scenario_basic.toml, 28 核):

| 取活开销 | 总时长 | 对静态分核 |
| --- | --- | --- |
| 静态分核 | 1751.48 | +0.00% |
| 0 (缺省) | 1727.97 | **-1.34%** |
| 0.02us | 1730.43 | -1.20% |
| 0.05us | 1734.12 | -0.99% |
| 0.1us | 1744.15 | -0.42% |

**那 1.34% 在取活开销约 0.15us 处被吃光。** 所以"开晚绑定更快"这个结论完全取决于一个
没测过的量。`analysis/sensitivity.py` 把它登记为 `Unknown` (连范围都没有, 不参与区间
传播 —— 编一个范围就是把无知包装成精度), 于是 `examples/run_uncertainty.py` 里晚绑定那
一行判定为**不可判定**, 尽管它的区间反而是最窄的 ([-1.39, -1.25])。窄区间不等于可信。

### 要什么 run

同一形状、同一 tiling, **只换分核方式**两版:

1. 静态分核版: 每核按 block 号算出自己的 tile 列表 (= 那份实现的 `startBlockIdx` 轮转);
2. 动态取活版: 一个 GM 上的共享游标, 每核循环 `atomic_add(cursor, 1)` 取下一个 tile。

两版的总时长差 = (晚绑定省下的等待) - (取活开销 x 取活次数)。取活次数已知 (= tile 数),
所以一次差分就能把 `late_bind_fetch_us` 反解出来。
**要点**: 第 2 版必须跑在 tile 数远多于核数的形状上, 否则取活次数太少, 开销被噪声盖住。

建议同时打点原子加本身的耗时 (取活前后各一个时间戳), 这样拿到的是直接测量值而不是
差分反解值 —— 差分里混着调度顺序变化带来的二阶效应。

## R8 — 分段就绪的每段同步开销 (新增 2026-10-08)

`StageLink.segment_sync_us` 缺省 **0.0**, 出处 assumed —— 同 R7, **0 不表示没有代价**。

### 为什么要它

`readiness` 把一个消费者沿共享轴拆成 S 段, 第 j 段只等覆盖自己那段的产出。模型里
拆段只有收益 (开工更早), 没有代价; 真实实现每段要多走一次标志等待/轮询。不计这笔,
**分得越细就永远不会更差** —— 和 R7 的晚绑定一样, 是模型的结构偏置, 不是结论。
所以缺省下 `readiness="per_chunk"` 扫出来的收益是**上界**。

### 要什么 run

同一形状、同一 tiling, 只换 GMM2 沿 K 的分段数两版 (S=1 等齐 / S=每个 kL1 块一段),
测每个 GMM2 tile 从"上一段算完"到"本段标志等待返回"的时间。要点:

- 窗口不能取整个等待区间 —— 那一段含"生产者还在算", 既与生产者时长重复计费,
  又会让这个本该与载荷无关的量带上尺寸依赖 (与 `PipelineConstraints.sync` 同一个坑);
- 形状要选 K 块数远多于 1 的 (块数 = ceil(K / kL1)), 否则两版的段数一样, 差分为 0。

反解: 总时长差 = (细分段省下的等待) - segment_sync_us x (多出来的段数), 段数两版都已知。

## 做完之后怎么确认模型真的准了

1. `python tools/compare_measured.py <run_dir> examples/<run>.toml` 每个 stage 看偏差
   (两个都是位置参数, 没有 `--scenario`);
2. 六个 `examples/*.toml` (现有三个 batch x shared/noshared) 全部跑一遍, 记下每个 stage 的
   `stage_busy_us` 偏差与总时长偏差;
3. 偏差写进 `README.md` 的"精度边界"一节, **带上标定域** —— 域外的结论不作数。

## 现有六个 run 能定什么、不能定什么

| | 能 | 不能 |
| --- | --- | --- |
| 20260930 bs36 / bs128 (1 个 m-group) | 固定 m-group 数只变 m -> 已定下"载入是相加"与 A 流斜率 | 并发只有 28 与 18 两档, 定不了带宽曲线 |
| 20260930 bs8192 (12 个 m-group) | 与 bs128 等 m 对比 -> 定出 B 流复用比例 f ≈ 0.53 (一个点) | 一个点不是规律 |
| 三者合看 | COMBINE 对 m 超线性这个**事实** | 分不出"m 的效应"与"token 数的效应" —— 这正是 R3 要解决的 |

### 2026-10-04 把 trace 榨到底之后的修订

把 `args.payload` 按 `GMMAddrInfo::ProfileTile` 解回 `(专家, 波次, m 组, N 组)`、
并去掉 `pid=0/1` 的重复记录之后, 上面那张表要改三处:

- **"COMBINE 对 m 超线性"不是一条干净的事实。** bs128 与 bs8192 每事件行数相同
  (256 行 x 256 列), 而 bs8192 的最快 tile (11.3us) 比 bs128 的最快 tile (22.7us)
  **快一倍**。同一个 bs8192 run 内部, m 组 0/1/2 中位 11.46us、m 组 9/10/11 中位
  55-58us —— 字节完全一样。所以 COMBINE 时长的主要变化来自**别的阶段挤进来的带宽
  争用**, 不是 tile 自身的 m。本模型不建模带宽争用, 所以 COMBINE 公式应当对标**最快**
  那条, 争用那部分留给"模型是乐观的"这个已知边界。
- **R4 不再是纯粹的待办: 现有数据给了它一个量级。** 对标最快的 tile 反扣出每核跨卡写
  ~8.6 GB/s (bs8192 9.5 / bs36 7.8 / bs128 4.5), 原先"与读侧对称 = 31 GB/s"的假设
  被排除。`BW_REMOTE_WRITE` 已据此从 31000 改为 8600。R4 仍要做 —— 为的是把
  "每行固定开销"与"按字节"分开, 不再是为了定量级。
- **R3 用现有 run 一定做不出来。** 路由是 cyclic 近均匀 (每专家来自四卡 62-66 行,
  ±3%), 而专家间 COMBINE 时长差 ±12%; 跨卡行数的差异被噪声盖住, 没有第二个回归轴。
- **R1 不能靠 `args.cycles`。** `config.json5` 里 `timestamp_frequency_mhz = 1000`,
  `cycles` 恰好等于 `dur`(us) x 1000 —— 它是 1GHz 时间戳计数, 不是 Cube 主频。
- 顺带: `data/*bs8192*trace_rank0.json` 被打点容量截断 (7.6MB 处断在一个事件中间),
  解析要先截到最后一个完整事件再补括号; 截断后仍有 2470 条 COMBINE 可用。
